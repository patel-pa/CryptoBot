# Monitoring

Prometheus collects numbers from the cluster every 30 seconds, Grafana shows them and raises
the alert. Both come from the Helm chart
[kube-prometheus-stack](https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack)
(version 93.3.0); this folder holds our settings and our own dashboards and alert rule.

| File | What it is |
|---|---|
| `values.yaml` | The chart's settings: scrape the API, no Alertmanager (nor the built-in rules that need it), no unreachable control-plane targets, 2 days of data without a persistent volume, Grafana's loaders for our dashboards and alert rules |
| `dashboards/api.json` | Grafana dashboard *CryptoBot / API*: traffic, 5xx errors, response times, forecasts stored, memory and CPU (from the API's `/metrics`) |
| `dashboards/jobs.json` | Grafana dashboard *CryptoBot / Scheduled jobs and pods*: the latest result of `ingest` and `retrain`, time since their last success, next run, run durations, failed Jobs, pods not ready, restarts, memory |
| `alerts/failed-jobs.yaml` | Grafana alert *Scheduled job failed*: the latest run of a CronJob (scheduled or started by hand) failed |
| `kustomization.yaml` | Turns the dashboards and the alert rule into ConfigMaps that Grafana loads by their labels |

What the chart installs (namespace `monitoring`):

| Part | Job |
|---|---|
| Prometheus | Scrapes its targets every 30 s and keeps 2 days of data on the pod's own disk |
| kube-state-metrics | Turns Kubernetes objects into numbers, e.g. when a CronJob last started a run and when a run last succeeded |
| node-exporter | CPU, memory and disk of every node |
| Prometheus Operator | Configures Prometheus from Kubernetes objects such as the ServiceMonitor `cryptobot-api` |
| Grafana | Dashboards and alerts; its loaders (sidecar containers) pick up ConfigMaps labelled `grafana_dashboard` or `grafana_alert` |

Nothing is reachable from outside the cluster (no Ingress, no load balancer) and nothing is
kept on a persistent volume (no PersistentVolumeClaim, no EBS volume), so the stack adds
nothing to the teardown steps.
Grafana keeps no state of its own either: after a restart it loads everything again from
these files. Its admin password is generated by the chart into the Secret
`kube-prometheus-stack-grafana`.

## On kind

After the app runs (see "Run on Kubernetes locally (kind)" in the main README), from the
repository root (needs Helm 3.8 or newer, which can install charts from an OCI registry):

```bash
helm upgrade --install kube-prometheus-stack \
  oci://ghcr.io/prometheus-community/charts/kube-prometheus-stack --version 93.3.0 \
  --namespace monitoring --create-namespace -f monitoring/values.yaml
kubectl apply -k monitoring                       # our dashboards and alert rule
kubectl -n monitoring get pods                    # wait until all are Running

# Grafana on http://localhost:3000, user admin, password:
kubectl -n monitoring get secret kube-prometheus-stack-grafana -o jsonpath='{.data.admin-password}' | base64 -d; echo
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80

# Prometheus on http://localhost:9090 (Status > Target health: the api target is UP)
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090

# remove it again (the chart's CRDs stay; `kind delete cluster` removes everything)
kubectl delete -k monitoring
helm uninstall kube-prometheus-stack --namespace monitoring
kubectl delete namespace monitoring
```

In PowerShell, read the password with
`kubectl -n monitoring get secret kube-prometheus-stack-grafana -o jsonpath='{.data.admin-password}' | ForEach-Object { [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($_)) }`.

In Grafana: **Dashboards > CryptoBot** holds the two dashboards (choose the namespace at the
top: `cryptobot` on kind, `dev` or `prod` on EKS); **Alerting > Alert rules** shows
*Scheduled job failed* in the same folder. The chart's own Kubernetes dashboards (cluster,
nodes, pods) are listed at the top level of Dashboards.

## On EKS

The platform layer installs the same chart with this `values.yaml` and creates the same
ConfigMaps from these files (see `infra/terraform/platform/README.md`), so Grafana is
complete after `terraform apply`. Open it with the same port-forward command.

## The alert: "Scheduled job failed"

Every run of a CronJob is a Job, scheduled or started by hand
(`kubectl create job --from=cronjob/ingest ...`). Kubernetes keeps the last 3 successful and
the last 3 failed runs of each CronJob (`k8s/base/cronjobs.yaml`), and kube-state-metrics
reports when each started and how it ended. The alert fires for a CronJob when its **newest
failed run started after its newest successful run**, or when it has no successful run at
all (the first run in a new environment):

| Time | `ingest` run | Newest failed run | Newest successful run | Alert |
|---|---|---|---|---|
| 10:00 | succeeds | – | 10:00 | Normal |
| 10:15 | fails twice (`backoffLimit: 1`) | 10:15 | 10:00 | **Firing** |
| 10:30 | running … | 10:15 | 10:00 | **Firing** (not fixed yet) |
| 10:31 | … succeeds | 10:15 | 10:30 | Normal |

Why not simpler rules: "a failed Job exists" would stay red for hours after the problem is
gone, because failed Jobs stay in the history (the chart's built-in rule `KubeJobFailed`
works that way: it clears only when you delete the Job). "The CronJob's last start is newer
than its last success, and no run is active" goes back to Normal whenever the next run
starts, so a broken job would make the alert flap every 15 minutes (seen in a test on kind).

There is no notification channel (e-mail, chat): the alert shows in Grafana, on the
*Scheduled jobs* dashboard (the panel "Latest run of each scheduled job" uses the same
test) and under Alerting. The chart's built-in Prometheus rules are evaluated too, but with
Alertmanager switched off they only show in Grafana's alert list. The built-in rules that
need an Alertmanager are switched off in `values.yaml`: its own rules (useless without it),
`PrometheusNotConnectedToAlertmanagers` (always true without it), and `Watchdog` and
`InfoInhibitor` (they fire on purpose to feed it), which would otherwise show as firing forever.

**Test it** (namespace `cryptobot` on kind; `dev` on EKS): make `ingest` fail with an invalid
setting and run it once by hand (or wait for its next scheduled run); the alert fires within
about a minute after the run failed (Prometheus reads the cluster every 30 s, Grafana checks
the rule every minute). **Wait until it shows Firing before you undo it:** the rule compares
the start of the newest failed run with that of the newest successful run, so if the fixed run
succeeds before Grafana's next check (every minute, on data up to 30 s old) has seen the
failure, the alert never fires. Then undo it
and run `ingest` again; the alert clears within about a minute after that run succeeded.

```bash
kubectl -n cryptobot delete job ingest-broken ingest-fixed --ignore-not-found # Jobs of an earlier test
kubectl -n cryptobot set env cronjob/ingest HISTORICAL_LOOKBACK_DAYS=broken   # break it
kubectl -n cryptobot create job --from=cronjob/ingest ingest-broken           # fails after 2 tries (~30 s)
# wait until Alerting > Alert rules shows "Scheduled job failed" as Firing (about 1-2 minutes)
kubectl -n cryptobot set env cronjob/ingest HISTORICAL_LOOKBACK_DAYS-         # undo (back to the ConfigMap's value)
kubectl -n cryptobot create job --from=cronjob/ingest ingest-fixed
```

## Changing a dashboard

The dashboards are provisioned from files, so Grafana does not save changes to them. Edit
in Grafana, then **Export > Export as JSON** (no "export for sharing externally"), replace
the file in `dashboards/` and run `kubectl apply -k monitoring` again; Grafana loads the new
version within seconds. On EKS these ConfigMaps belong to the platform layer: commit the file,
then plan and apply `infra/terraform/platform` (a `kubectl apply -k monitoring` there is only
a preview until the next apply). Keep the `uid` (links and bookmarks use it) and the datasource
`prometheus`, which the chart creates.
